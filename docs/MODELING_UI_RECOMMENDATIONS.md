# Modeling capabilities the UI can expose

Living handoff from modeling to UI, 4–5 November 2026. These are suggestions for the UI agent to adopt, adapt or defer against its own plan; they do not require a new screen for every endpoint. Prioritize the existing Phase 1 flow and motion acceptance gate. Wire shapes and runnable fixtures in `contract/` take precedence over this guide. Modeling updates this document when it publishes a capability.

## Current integration priorities

The backend supports explicit Intake and independent Safety review, but those explicit steps are still missing from the shared dev UI. Prioritize them before adding more result panels. Keep the held UI branch separate until its compatibility issues are resolved; [UI_COMPATIBILITY_REVIEW.md](overnight/UI_COMPATIBILITY_REVIEW.md) records that review. Advance-arrival planning is available through the supplied-series API; a production public forecast composer remains unavailable.

Source confidence and qualification are different: a record labeled `published` does not prove its rating was verified. Use the qualification response and its issues, not a provenance label, for capability claims. Static load/holding results evaluate wind and current only; wave/wake loads and maneuvering response remain outside that assessment. A wave-height display is not evidence that wave forces were included.

## Advance docking planning (optional compact panel)

A practical first UI is an arrival-window form next to the existing planner, followed by a table/timeline of alternatives. Keep the detailed modeling controls collapsed.

1. Show **planning as-of time**, candidate arrivals at least 24 hours later, operation duration and holding duration. Display UTC alongside a clearly named local timezone. Fetch enough coverage to include the end of holding, not just the next 24 hours.
2. Show source, issue time (when actually supplied), separate retrieval time, valid interval, coverage gaps, missing components and any unknown wind averaging basis before submission. A training scenario is not a weather forecast. Do not label retrieval time as provider issuance; tidal predictions and weather forecasts have different provenance. Public composite forecasting is still being integrated; supplied complete snapshots already work. CBOFS sampling retains grid cell and depth: surface guidance must not silently replace missing deeper currents, and a nearby wet cell is not a surveyed pier reading. The reader is not yet a complete forecast endpoint.
3. Submit `POST /api/v1/mooring/forecast-plan`, follow its job, and display `ForecastDockingResponse`. Full request: `contract/examples/modeling/mooring_forecast_plan.json`; details: [FORECAST_DOCKING.md](FORECAST_DOCKING.md).
4. Render each arrival's computed outcome, governing time/element, utilization and result links. Distinguish unavailable inputs from undetermined computation and an assessed overloaded plan. If no arrival has a complete usable assessment, aggregate validity is invalid/RED; an assessed overloaded result can remain limited/RED. One bad snapshot need not abort other arrival alternatives. A selected arrival only means the static sampled holding checks met the requested target; it does not approve navigation or line handling.
5. Offer to inspect/apply the returned line configuration using the existing map. Use `selected_config` (when present) for the chosen arrival: preserve each line’s `paid_out_unstretched_length_ft` and wet/dry condition plus the returned installation tide. The common `config` describes assignments across alternatives. These are modeled reproducibility values, not rope-cutting or handling instructions. Retain forecast provenance and tug assumptions. `optimize_lines` searches a common configuration; no synthetic conversion from utilization into a new line rating.
6. Show a **recheck required** state when forecast, arrival, loading, geometry, lines or tugs change. Do not visually carry a previous approval onto changed inputs. Backend results remain immutable; automatic UI invalidation/replanning is a suggestion, not yet implemented here.

Draft sequences preserve the scenario loading/MST and check staged line parts and tug release. Show each step’s state as within limits, blocking or undetermined, retain `sequence_result_id`, and keep the unreviewed label visible. Printable sheets now include those notes and the result reference. Invalid tug assessments are excluded from assistance and leave the plan blocked. Draft sequences use the existing sequence/planner/review interfaces; the forecast result does not currently bundle an approved sequence. Keep durations and intermediate handling assumptions labeled unreviewed. Pilot/deck-officer acceptance, UKC, tug availability and traffic are separate requirements.

## Risk displays

The gust-model endpoint now projects the committed fitted artifact and reports its unqualified status in provenance; it no longer invents directional detail for an artifact without sectors. Exploratory sector fits, when present, are not independently validated and are not used by the global risk sampler. Keep probabilities labeled as scenario outputs when the uncertainty model is unqualified. Show failed-solve counts and bounds beside percentages. Horizon `p_event` is the known-exceedance fraction and only a lower bound when trajectories fail; use `p_event_bounds` and the widened `p_event_ci95`, not a green badge based on the lower bound. An all-failed calculation is invalid/RED. `effective_step_min` gives the actual sampling interval including both horizon endpoints; events between samples remain unresolved. Ship fittings are included alongside lines, pier fittings and fenders.

Risk timeline can consume exact supplied `forecast` snapshots with explicit `start_utc`, endpoint coverage and <=60-minute gaps. Show each step’s environment/validity and the result’s `forcing_source`. Omitted forecast is always labeled synthetic training; never call it NOAA output merely because a provider is enabled. Supplied knots are all evaluated, independent of the legacy display interval.

Live `/ws/alerts` messages now carry optional `validity`. Invalid environmental or plan inputs produce RED with no usable utilization; seed-data assessments remain explicitly limited. Observation-only messages do not establish mooring adequacy. Within one connection, alerts preserve the initial assessed installation tide as conditions change; explicit paid-out lengths remain authoritative. Reconnecting a scenario without explicit lengths establishes a new connection-time installation assumption, not a persisted plan installation. They do not retension lines at each new tide within that connection. Show validity reasons alongside severity and stale state.

## Integration checklist for the UI agent

- Regenerate types after merging `dev`; use generated examples as consumer fixtures. Report missing/ambiguous fields in `docs/overnight/modeling-agents.md` → Requests.
- Keep seed/synthetic/limited labels visible on map, alternatives and sheet, including when a review is ready for signature.
- Display partial/stale/missing forecasts without filling values. Future missing coverage is a risk finding, even if present conditions look moderate.
- Auth is off for the local demo. Optional authenticated HTTP/SSE clients need headers; never place bearer keys in URLs. Do not infer verified approver authority from a typed name.
- PDF is verified with the documented native-library setup in `agents/README.md`; it may return 501 when the renderer is unavailable; HTML remains usable for browser print. Show the actual renderer result.
- Report which suggestions were picked up in the UI inbox's Interfaces section. Defer optional forecast/training panels if they jeopardize the required end-to-end flow.

## Coordination

The isolated review of `ui/frontend-updates` is recorded in [UI_COMPATIBILITY_REVIEW.md](overnight/UI_COMPATIBILITY_REVIEW.md). Its owner-directed no-merge hold remains respected; the review lists concrete compatibility and browser blockers.

Use the shared inbox protocol in [team_agent_instructions/README.md](../team_agent_instructions/README.md). Watch `origin/dev`, active UI/data/modeling branches and the three `docs/overnight/` files at each integration point. Publish endpoint changes, fixtures, assumptions and test status before consumers depend on them. Never auto-merge unchecked work or edit another agent's worktree.

`/ws/alerts` resolves the same scenario source for every frame. Terminal close 1013 means the source is unavailable (no replacement snapshot); 4404 means unknown/unowned scenario or reference; 4400 means invalid timing/reference. Show unavailable rather than retaining an apparently live utilization. Reconnect with backoff after a transient provider failure.

Direct saved-scenario `replay`/`forecast` modes are not implemented by the shared snapshot resolver and are rejected. For recorded playback use an explicit environment scenario; advance planning uses the supplied-series forecast endpoint. Saving a mode name does not establish a data feed.

Optional forecast source panel: display `metadata.components` separately for wind, current and water level, including source, validity interval, quality and limitations. Label `retrieved_at_utc` as “retrieved”, never “issued” or forecast age. The advance-planning result exposes separate actual issue and retrieval lists. Unknown issue time stays limited even when retrieval establishes availability before planning. This is a consumer interface, not a claim that the live composite forecast provider exists.

For a saved scenario's current forcing, `GET /scenarios/{id}/environment` follows the same source resolver used by the agents, alerts and simulation initialization. Explicit mock stays synthetic under a configured public provider; unsupported replay/forecast mode names return 422. The legacy `live` mode means the configured default provider and can still return labeled mock data in the offline demo. Render the returned source, not a presumed source based on the mode name. This endpoint does not supply a forecast or persist a time-frozen environment.

Intake for an explicit mock scenario rejects a returned public forecast instead of mixing sources, and omits provider-based berthing windows. Missing matching coverage remains a RED data-quality issue; the current synthetic snapshot is not a promise about tomorrow.

Line details: `length_ft` is the stretched straight span at the solved pose; `paid_out_unstretched_length_ft` in the resolved config is a different input. Horizontal lead angle is relative to the yawed ship, not the fixed pier axis. Line-geometry rule findings now use the same unrounded solved span/angles as the displayed result. Keep these distinctions in labels; neither field is a deck cutting instruction. Nominal layout checks such as bow placement remain separate.

Printable sheets now include the intake forecast assessment, current flow-toward bearing, assessed water level and recorded wind basis. Component issue/retrieval/validity/quality are rendered separately when supplied; missing basis remains explicitly unknown. The existing HTML/PDF endpoints carry this automatically. Preview/print should retain that context and the limited-validity banner.

Component quality can invalidate a reading even when its numeric values and aggregate quality are unchanged. Display Intake `data_quality` and watch `recheck_reasons`; do not preserve an old utilization percentage after `requires_recheck`. Unknown issue time and declared source limitations remain visible informational findings, not invented freshness.

Intake headlines now retain blocking input-quality qualifications even when no physical threshold window is detected. Do not truncate the headline before that qualification. Printable sheets include the planner's assessment assumptions and limits. Ordinary Intake selects representative snapshots (peak gust, strongest broadside current, current conditions); it does not prove every intermediate forecast sample is supported. For an arrival/holding interval use `/mooring/forecast-plan` and retain its sample coverage and validity.

Ship selection already labels classes without fittings as “hull only.” Preserve that distinction: CG-47, LHD-1 and CVN-68 have environmental-load inputs but no seed mooring-fitting layouts. Disable line-plan actions or show the explicit missing-layout error for these classes; never populate another ship's fittings. DDG-51-FIIA is the supported seed mooring demonstration, still limited.

On macOS with installed Homebrew Pango libraries, the verified stack launch is `make mock PDF_LIBRARY_PATH=/opt/homebrew/lib` (Intel Homebrew: `/usr/local/lib`). Setting `DYLD_FALLBACK_LIBRARY_PATH` outside system `make` can lose the variable. Keep the explicit PDF501→HTML/browser-print fallback on hosts without renderer libraries.

Berth registration now rejects changed data under an existing ID with HTTP409; identical retries remain accepted. Preserve the saved reference and request a new draft/revision ID for edits. Do not retry a conflicting overwrite or imply that an existing scenario automatically uses edited geometry. Vision's first confirmation is unchanged; a revised confirmed draft requires a new vision job.

Keep `line_number` unique when adding, duplicating or importing lines. Duplicate IDs now return422 rather than producing ambiguous result/sequence references. Gaps are allowed, and the backend does not silently renumber user lines.

The agent currently implements only `objective=moor_for_forecast` with empty constraints. The existing selector also lists storm preparation and berthing; disable or mark those unavailable until their execution paths exist. A forecast-only plan does not establish MST storm-design compliance or approve the approach/contact maneuver. Do not relabel an unsupported objective as a forecast plan silently.

Safety warning SSE follows the plan’s saved source. A terminal `source_unavailable` event means monitoring has stopped; clear any apparent live status and offer an explicit retry. A warning with `requires_recheck` and absent `pct_of_wll_limit` must not retain the last numeric percentage. Temporal availability failures also trigger this state.

For warning streams, show the age of `at_utc`, not just the time a message arrived in the browser. A delayed connection can deliver old messages. Keep an explicit delayed/disconnected state, retain source labels, and require a fresh assessment before presenting an old warning percentage as current. The Safety SSE stream is not a guaranteed latest-frame channel; choose and document a UI freshness policy rather than inventing one from the stream’s polling interval.

Confirmed berth persistence: with file-backed MOORING_DB, a confirmed catalog entry remains selectable after restart or restore. Retrying unchanged confirmation is idempotent; changed geometry needs a new draft/berth ID. A suggested UI should distinguish saved geometry from engineering approval and should not promise restart durability in the default in-memory demo. Catalog visibility is shared, not per-user private.

The direct recommendation apply path now replaces the old tug fleet with candidate.tugs, including empty, before reanalysis. Preserve that behavior when adapting the UI. For sheet imagery, verify that a captured map depicts the selected plan; the current view may have changed since planning. A mismatched current-map capture should be omitted or clearly separated from the archived plan, never presented as its assessed layout.

Direct recommendation candidates now expose optional resolved_config alongside assignment-only config. Apply resolved_config when present to preserve the assessed unstretched lengths and wet/dry condition, and retain candidate.tugs. The shared UI does this, sends selected standoff and current assistance to search, discards results if assistance changes in flight, and rejects stored candidates after their geometry context changes. Forecast-arrival planning still uses assignment-only config to evaluate each arrival’s installation separately.

Request ship-specific Intake (scenario_id, or berth_id plus ship_class_id and side_to) before planning/review. A berth-only report can describe environmental concerns but leaves ship MST unknown; Safety reports an unresolved AMBER check rather than passing it. Keep all aggregate/component out-of-range findings visible, including samples that are not the selected peak condition.

Risk requests can return422 for a combined solve budget above25,000, even when each individual field is within its range. Show that error and let the user explicitly reduce the sampling/horizon workload. Do not silently change sample counts. Supplied timelines solve every provided knot; changing the reporting interval alone does not remove those knots. Existing UI requests remain within the cap.

Shared dashboard risk display fixes: invalid/unknown validity or no successful samples withholds probability numbers; absent element MBS stays n/a. Usable zero scenario statistics still display zero. Pointwise results are labelled instantaneous, and the legacy generated timeline is labelled synthetic training rather than a weather forecast. Fender risk compares energy against rated energy while its lbf percentile fields now report reaction force. Preserve these meanings in the held UI branch; backend=real alone is never a display qualification.
